## UPGRADING

To upgrade from 3.x to 4.x you will not be able to keep the virtual file system
or slave files. Userfiles will be converted correctly if password is not encrypted.

Follow the installation documentation and do now install into the version 4.x:

https://github.com/drftpd-ng/drftpd/blob/master/README.md

Next if you have user files that predate 4.x, they need to be converted. There is a script in "TODO"
that is called "TODO: Migrate-v3-to-v4.sh". Next start the master and readd slaves.
Themes and all .conf files have to be rebuild in 4.x. Copying over the files will
give you alot of problems. The virtual file system will be built when slaves are
merged for the first time.

## To upgrade from 4.x to the latest:

Before performing a upgrade of DrFTPD, make sure to delete the following folders:
- src

### Compile
- Run mvn clean
- Run mvn validate
- Run mvn install

Regarding the configuration files, check that you are using the new ones once the build is done.

### Upgrading to 4.0.12: search index (Lucene 3.6 -> Lucene 10)

Build with "mvn clean install" (not just "mvn install"): the clean step removes the old
lucene-core/lucene-queries 3.6.2 jars from runtime/master/lib, they must not stay next to
lucene-core 10.

The search index (userdata/index) written by previous versions can't be read anymore. Nothing has
to be done by hand:
- On the first start the master logs a warning, renames userdata/index to
  userdata/index.incompatible-<date> (nothing is deleted) and creates a new index.
- Once the plugins are loaded, it rebuilds the index from the virtual file system in the
  background, like SITE REBUILDINDEX does. Until it is done, SITE SEARCH/FIND, the dupe checks
  (dupecheck plugin) and the IMDB/TvMaze listings built from the index only see part of the site.
  SITE INDEXSTATUS FULL shows "rebuild: in progress" with the progress meanwhile.
- How long it takes: the rebuild walks the whole VFS (userdata/vfs) and indexes every file and
  directory, reading the inode of each one from its JSON file on disk. The time is roughly
  proportional to the number of inodes, and depends mostly on the disk of the master (and on its
  file cache: a second rebuild is faster than the first one). There is no fixed figure; to get an
  estimate for your site, look at the master log: every 30 seconds it logs a line such as
  "Index rebuild in progress: 120000 inodes indexed in 0h01m00s (2000 inodes/s)". Divide the
  number of files and directories of your site ("find userdata/vfs | wc -l" gives an upper bound)
  by the rate shown after the first minute or two. The end is logged as "Index rebuild done: ...".
  The master serves clients meanwhile, but the rebuild causes disk I/O on the master.
- If the master is stopped before the rebuild is done, the index is flagged as incomplete and the
  rebuild starts again on the next start. The same goes for an interrupted SITE REBUILDINDEX.
- No index backup is made while a rebuild is required or running.
- If the automatic rebuild fails (see the master log), run SITE REBUILDINDEX.
- Once the new index is complete, the userdata/index.incompatible-<date> directory and the old
  backups in index.bkp (also Lucene 3.6 indexes) can be deleted.

Downgrading to a previous version after that requires restoring the old index directory (or
running SITE REBUILDINDEX with the old version).

The -regex option of SITE SEARCH/FIND keeps the java.util.regex syntax and must still match the
whole path. Third party plugins implementing IndexDataExtensionInterface or
QueryTermExtensionInterface have to be ported (the in-tree zipscript, imdb and tvmaze plugins
show how).
